# 工作流程（全栈任务优先）

在 [任务优先工作流](task-first-workflow.md) 基础上扩展为全栈开发。本文档只说明全栈带来的增量；工作流、状态机、回写规则、文档结构均沿用原文档。

## 全栈任务范围

任务不再限于前端 UI，涵盖完整技术栈：

| 层 | 典型任务 |
| --- | --- |
| 前端 | 页面、组件、样式、交互 |
| 后端 | 接口、服务、中间件、定时任务 |
| 数据 | 数据库 schema、迁移、索引 |
| 全栈 | 跨端联调、配置部署、端到端功能 |

「本方」指当前任务的负责方，可以是前端、后端或全栈。状态机不变，但判定「能否闭环」需考虑前后端联动。

## 任务粒度：优先按接口切

后端的任务建议以**接口**为圆心来组织，这比按文件或按目录组织更容易对上需求，也更容易写出可执行的验证条件：

- 改一条接口的入参、返回值、处理逻辑 → 一条任务，接口即任务边界。
- 一次需求动同一模块的多条接口 → 按接口拆成多条任务，各自对应一个接口节点。
- 全局能力（请求体解析、鉴权、限流、超时、错误格式）→ 一条任务，对应的总览节点用 `route: "*"` 表示全部接口。
- 纯内部重构、工具函数、schema 迁移 → 一条任务，这类没有对应接口，任务里写清涉及的代码位置即可。

判断口径：**外部能观测到的行为变化**用接口作为边界，**内部实现调整**用模块作为边界。任务标题带上前端/后端归属会更清楚，比如「用户服务-实现登录接口」「登录页-对接登录接口」。

## 风险评估补充

在全栈场景下额外关注：

- **接口契约变更**（请求/响应结构、鉴权方式）→ 高风险，前后端需同步，确认兼容策略；如果是破坏性变更，优先加版本号或并行新旧接口。
- **全局生效的改动**（`route: "*"` 类）→ 高风险，一次改动影响所有接口，说清影响面和回归范围。
- **数据库 schema 变更**（加字段、改类型、迁移）→ 高风险，影响存量数据，确认回滚方案。
- **跨端依赖**（前端等接口、后端等 UI 对接）→ 中风险，确认先行模拟还是等待。
- **环境配置变更**（端口、环境变量、依赖版本）→ 中风险，确认影响范围。

## 验证条件补充

验证条件可以包含非 UI 部分，按实际交付层选择，接口类任务建议至少写一条可直接执行的调用：

- 接口验证：调用接口确认返回结构和状态码。
- 数据验证：查询数据库确认数据已写入或更新。
- 日志验证：检查服务日志确认无异常。
- 端到端验证：从前端操作触发，确认后端响应正确。
- 全局改动验证：至少覆盖一条正常接口和一条异常接口，确认中间件对所有接口生效。

## 任务标题示例

- `用户服务-实现登录接口`（后端）
- `登录页-对接登录接口`（前端联调）
- `全站-请求体解析上限调整为 20MB`（全局，对应 `route: "*"`）
- `用户中心-打通登录流程`（全栈）
